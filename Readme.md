# Lab5 - Branch Predictor

本项目实现了 9 种分支预测策略，在 13 个 trace 文件上测试并对比预测准确率。

## 项目结构

```
lab5/
├── predictor.c      # 分支预测器实现（所有实验代码）
├── run_all.sh       # 并行自动化测试脚本
├── Makefile         # 编译配置
├── Result.xlsx      # 实验结果汇总
├── CLAUDE.md        # Claude Code 协作说明
├── traces/          # 13 个 BT9 格式 trace 文件
│   ├── LONG_MOBILE-1~4.bt9.trace.gz
│   └── SHORT_MOBILE-1,2,3,4,24,25,27,28,30.bt9.trace.gz
└── logs/            # 每次测试的完整输出日志
```

## 快速开始

### 单次运行

```bash
make
./predictor traces/SHORT_MOBILE-24.bt9.trace.gz
```

### 批量并行测试

```bash
./run_all.sh          # 自动 make clean + 编译 + 并行测试所有 trace
JOBS=4 ./run_all.sh   # 限制并发数为 4
```

脚本会自动完成：`make clean` → `make` → 并行运行全部 13 个 trace → 输出每个 trace 的完整结果 → 打印 MISPRED_PER_1K_INST 汇总表。

## 实验设计思路

### 共同基础

所有实验都围绕 `predictor.c` 中的三个核心函数实现：

- `PREDICTOR_init()` — 初始化预测器状态（分配表、设置初始值）
- `GetPrediction(PC)` — 根据当前 PC 地址给出预测（TAKEN / NOT_TAKEN）
- `UpdatePredictor(PC, resolveDir, ...)` — 根据分支实际执行结果更新预测器状态

核心预测元件是 **2 位饱和计数器**（值 0-3）：≥ 2 预测 TAKEN，≤ 1 预测 NOT_TAKEN。实际跳了 +1，没跳 -1，范围卡在 [0, 3]。2 位计数器比 1 位更稳定，需要连续两次错误才会翻转预测方向。

---

### 实验 1：static（总是预测 Taken）

**思路**：最简单的静态预测，不看任何历史信息，始终预测跳转。

```
GetPrediction(PC) → 直接返回 TAKEN
UpdatePredictor   → 什么都不做
```

**特点**：无状态、无学习。作为基线对比，反映 trace 中 Taken 的自然比例。

---

### 实验 2：gshare（PC XOR GHR, 17 位历史）

**思路**：利用全局分支历史 + PC 地址的组合信息做动态预测。核心创新是用 XOR 将两个维度压缩为一个 PHT 索引。

```
数据结构：
  GHR：17 位移位寄存器，记录最近 17 条分支的实际结果
  PHT：2^17 项，每项一个 2 位饱和计数器

预测：index = (PC ^ GHR) % PHT_SIZE → 读计数器
更新：计数器 +1/-1，GHR 左移并补入本次结果
```

**XOR 的意义**：相同全局历史下不同 PC 映射到不同表项，不同全局历史下相同 PC 也映射到不同表项，减少哈希冲突。

---

### 实验 3：2bits PC>>2

**思路**：去掉全局历史，只看 PC 地址本身。最朴素的动态预测器。

```
数据结构：
  PHT：2^17 项，每项一个 2 位饱和计数器

预测：index = (PC >> 2) % PHT_SIZE → 读计数器
更新：计数器 +1/-1，不维护任何历史寄存器
```

**PC>>2 的原因**：指令地址通常 4 字节对齐，低 2 位恒为 00，右移去掉无效位。每个分支独立学习自己的跳转倾向，分支之间互不关联。

---

### 实验 4：local PC>>2

**思路**：在 2bits 基础上引入**局部历史**——每个分支记住自己最近几次的跳/不跳模式，用这个模式查 PHT。

```
数据结构：
  BHT：2^17 项，用 PC>>2 索引，每项存 10 位局部历史
  PHT：2^10 项，用局部历史值索引，每项一个 2 位饱和计数器

预测：
  bhtValue = BHT[PC>>2]           // 取出该分支的局部历史
  counter  = PHT[bhtValue]        // 用历史值查计数器

更新：计数器 +1/-1，BHT 左移 + 补入本次结果 + 截断到 10 位
```

**与 2bits 的区别**：2bits 同一地址永远看同一个计数器；local 同一地址在不同历史模式下看不同计数器，能捕获"跳-不跳-跳"这种局部模式。

---

### 实验 5/6/8：gshare 变体（PC>>2, PC>>1, PC<<1）

**思路**：在原始 gshare 基础上，改变 PC 参与 XOR 前的移位方式，对比不同位对齐对预测效果的影响。

```
原始 gshare:  index = (PC      ^ GHR) % PHT_SIZE
gshare PC>>2: index = (PC >> 2  ^ GHR) % PHT_SIZE
gshare PC>>1: index = (PC >> 1  ^ GHR) % PHT_SIZE
gshare PC<<1: index = (PC << 1  ^ GHR) % PHT_SIZE
```

移位改变了 PC 的哪些位与 GHR 的哪些位做 XOR。由于指令地址低 2 位通常为 00，PC>>2 去掉无效位后对结果影响很小。PC<<1 改变了对齐关系，在某些 trace 上可能减少哈希碰撞。

---

### 实验 9：global（10 位全局历史）

**思路**：gshare 的简化版——完全不用 PC，只用 GHR 做 PHT 索引。

```
数据结构：
  GHR：10 位移位寄存器
  PHT：2^10 = 1024 项，每项一个 2 位饱和计数器

预测：index = GHR → 读计数器
更新：计数器 +1/-1，GHR 左移 + 补位 + 截断到 10 位
```

**特点**：表很小（仅 1024 项），硬件开销低。但不同分支的历史模式会冲突——分支 A 的行为可能把分支 B 的计数器带偏。去掉了 PC 维度后准确率明显下降。

---

### 实验 10：local（3 位局部历史 + 10 位 PC）

**思路**：与实验 4 类似的局部历史预测器，但参数不同——更短的局部历史，并将 PC 也拼入 PHT 索引以避免冲突。

```
数据结构：
  BHT：2^10 项，用 PC>>2 低 10 位索引，每项存 3 位局部历史
  PHT：2^13 项（10 位 PC + 3 位历史），每项一个 2 位饱和计数器

预测：
  bhtIndex = (PC>>2) & 0x3FF
  hist     = BHT[bhtIndex]
  phtIndex = (bhtIndex << 3) | hist    // PC 和历史拼接
  counter  = PHT[phtIndex]

更新：计数器 +1/-1，BHT 左移 + 补位 + 截断到 3 位
```

**与实验 4 的区别**：实验 4 的 PHT 只用局部历史索引（不同 PC 可能冲突），这里把 PC 也拼入索引，保证不同分支即使在相同局部历史下也不会冲突。但 3 位局部历史只能记录最近 3 次结果，模式捕获能力弱于实验 4 的 10 位。

---

### 结论

1. **gshare 系列整体最优**：四个 gshare 变体（PC>>2, PC>>1, 原始, PC<<1）结果非常接近，说明 PC 移位方式对预测影响不大，关键在于全局历史 + PC 的 XOR 组合
2. **local PC>>2 表现突出**：在 SHORT_MOBILE-27/28 上远超 gshare（0.03 vs 0.47），说明某些 trace 的分支行为更适合用局部历史捕获
3. **static 最差**：作为基线，反映了 trace 中 Taken 的自然比例
4. **global（无 PC）准确率明显下降**：验证了 PC 信息对区分不同分支的重要性
5. **历史长度影响大**：local 实验中，10 位局部历史（实验 4）显著优于 3 位（实验 10）
