# Lab5 - Branch Predictor

本项目实现了 11 种分支预测策略（9 种传统方法 + 2 种神经网络/高级方法），在 13 个 ARM trace 文件上测试并对比预测准确率。


## 一、传统方法实验设计（实验 2-10）

### 共同基础

所有实验都围绕 `predictor.c` 中的三个核心函数实现：

- `PREDICTOR_init()` — 初始化预测器状态
- `GetPrediction(PC)` — 根据当前 PC 给出预测（TAKEN / NOT_TAKEN）
- `UpdatePredictor(PC, resolveDir, ...)` — 根据实际执行结果更新预测器

核心预测元件是 **2 位饱和计数器**（值 0-3）：≥ 2 预测 TAKEN，≤ 1 预测 NOT_TAKEN。需要连续两次错误才会翻转方向。

### 实验 2：static（总是预测 Taken）

最简单的静态预测，不看任何历史信息，始终返回 TAKEN。无状态、无学习。作为基线对比，反映 trace 中 Taken 的自然比例。

### 实验 3：2bits PC>>2

最朴素的动态预测器。用 PC>>2 索引一张 2^17 项的 2 位计数器表。PC>>2 去掉指令地址低 2 位的无效对齐位。每个分支独立学习自己的跳转倾向，分支之间互不关联。

### 实验 4：local PC>>2

在 2bits 基础上引入**局部历史**——每个分支记住自己最近 10 次的跳/不跳模式。用 PC>>2 查 BHT（Branch History Table）获取该分支的历史模式，再用历史值查 PHT（Pattern History Table）中的计数器。能捕获"跳-不跳-跳"这种局部重复模式。

### 实验 5-8：gshare 系列

gshare 的核心是用 XOR 将 PC 和全局历史寄存器（GHR）组合为一个 PHT 索引，同时利用两个维度的信息。四个变体改变 PC 参与 XOR 前的移位方式：

| 变体 | 索引公式 |
|------|---------|
| gshare PC>>2 | `(PC >> 2) ^ GHR` |
| gshare PC>>1 | `(PC >> 1) ^ GHR` |
| gshare 原始 | `PC ^ GHR` |
| gshare PC<<1 | `(PC << 1) ^ GHR` |

均使用 17 位 GHR + 2^17 项 PHT。XOR 的效果：相同历史下不同 PC 映射到不同表项，相同 PC 下不同历史也映射到不同表项，减少哈希冲突。

### 实验 9：global（10 位全局历史）

gshare 的简化版——完全不用 PC，只用 10 位 GHR 做 PHT 索引。表很小（1024 项），但不同分支的历史模式会冲突，验证 PC 信息对区分不同分支的重要性。

### 实验 10：local（3 位局部历史 + 10 位 PC）

与实验 4 类似的局部历史预测器，但参数不同：3 位局部历史（记录最近 3 次），并将 PC 拼入 PHT 索引（`phtIndex = (PC_index << 3) | history`）避免不同分支冲突。3 位历史的模式捕获能力弱于实验 4 的 10 位。

### 传统方法实验参数对照表

| 实验 | 方法 | 表大小 | 历史类型 | 历史长度 | 索引方式 |
|------|------|--------|---------|---------|---------|
| 2 | static | 0 | 无 | - | - |
| 3 | 2bits | 2^17 | 无 | - | PC>>2 |
| 4 | local PC>>2 | BHT:2^17 PHT:2^10 | 局部 | 10 | PC>>2 → BHT → PHT |
| 5 | gshare PC>>2 | 2^17 | 全局 | 17 | (PC>>2) XOR GHR |
| 6 | gshare PC>>1 | 2^17 | 全局 | 17 | (PC>>1) XOR GHR |
| 7 | gshare 原始 | 2^17 | 全局 | 17 | PC XOR GHR |
| 8 | gshare PC<<1 | 2^17 | 全局 | 17 | (PC<<1) XOR GHR |
| 9 | global | 2^10 | 全局 | 10 | GHR only |
| 10 | local 3bit | BHT:2^10 PHT:2^13 | 局部 | 3 | (PC>>2, hist) 拼接 |

1. **gshare 系列整体最优**：四个变体结果非常接近，说明 PC 移位方式对预测影响不大，关键在于全局历史 + PC 的 XOR 组合

## 三、Perceptron 神经网络预测器

### 设计思路

Perceptron predictor（Jimenez & Lin, 2001）是第一个被证明在硬件上可行的神经网络分支预测器。核心思想：用单层感知机学习全局历史与分支结果之间的线性相关性。

### 代码逻辑

```
数据结构：
  权重表: 1024 项，每项 (20+1) 个 signed char 权重 [-128, 127]
  GHR: 20 位全局历史寄存器
  阈值 θ = 1.93 × 20 + 14 ≈ 52

预测（GetPrediction）:
  idx = (PC >> 2) & 0x3FF
  y = w[idx][0]                                  // bias
  for i in 0..19:
      y += w[idx][i+1] × (GHR[i] ? +1 : -1)     // 加权求和
  return y >= 0 ? TAKEN : NOT_TAKEN

更新（UpdatePredictor）:
  仅在 预测错误 或 |y| < θ 时训练:
    t = (resolveDir == TAKEN) ? +1 : -1
    w[idx][0] += t                                // 更新 bias
    w[idx][i+1] += t × (GHR[i] ? +1 : -1)        // 更新各权重
    权重截断到 [-128, 127]
  GHR 左移 + 补入本次结果
```

**阈值训练机制**：θ = 52 来自原论文的推荐公式。当 dot product 的绝对值已经很大时，说明模型对该预测有高度信心，此时不再更新权重，避免过拟合。

### 参数选择

| 参数 | 值 | 说明 |
|------|-----|------|
| TABLE_SIZE | 1024 | 权重表项数，用 PC>>2 低 10 位索引 |
| HIST_LEN | 20 | 全局历史长度 |
| 权重范围 | [-128, 127] | signed char，8 位整数 |
| θ | 52 | 训练阈值，1.93×HIST_LEN+14 |

### 运行方式

Perceptron 使用独立的 `perceptron.c` 和 `run_perceptron.sh`，不修改原始 `predictor.c`。脚本用 `perceptron.c` 替代 `predictor.c` 编译，生成独立二进制 `predictor_perc`。

### Perceptron 的局限性分析

1. **线性模型限制**：单层感知机只能学习线性决策边界，无法处理 XOR 类非线性关联
2. **纯全局历史特征**：不包含局部历史信息，对自身模式强（如"跳-不跳-跳"循环）的分支预测效果差
3. **表别名严重**：1024 项表面对数千万分支，冲突率高，远小于 gshare 的 131072 项
4. **冷启动开销**：权重从全零开始，短 trace 的学习不充分

## 四、TAGE 预测器

### 设计思路

TAGE（TAgged GEometric history length predictor，Seznec 2006）是 CBP（Championship Branch Prediction）竞赛的长期冠军。核心思想：**用多张表覆盖不同长度的历史，自动选择最合适的表做预测**。

TAGE 解决了前述所有方法的一个根本问题：不同分支需要不同的历史长度——有的看最近 4 条就够了，有的需要上百条。之前的方法（gshare、Perceptron）都用固定的历史长度，无法同时满足所有分支的需求。

### 代码逻辑

```
数据结构：
  Base 表:   8192 项 2 位计数器（bimodal，不用历史）
  Tagged 表: 8 张表，每张 4096 项
    每项: tag(12位) + counter(2位) + useful(2位)
    历史长度: 4, 7, 12, 20, 34, 58, 99, 168（几何递增）

预测（GetPrediction）:
  1. 从最长历史的表开始，找 tag 匹配的表
  2. 最长匹配 = provider，次长匹配 = alternate
  3. 如果 provider 的 useful > 0，信任 provider
  4. 如果 provider 的 useful = 0，用 alternate（可能是 base 或另一张表）

更新（UpdatePredictor）:
  1. 更新 provider 的 counter
  2. 仅当 provider 和 alternate 预测不一致时更新 useful
  3. 预测错误时，在更长历史的表中分配新条目（只替换 useful=0 的条目）
  4. 每 256K 次更新，所有 useful 右移 1 位（半衰，防止有用条目被错误保护）

GHR 更新: 64 位移位寄存器，每次左移 + 补入结果
```

**关键机制**：

- **Tag 匹配**：每张表用 PC + GHR 的哈希计算 index 和 tag，只有 tag 匹配才认为该条目"有效"
- **Useful 计数器**：2 位计数器，记录该条目是否被证明有用。防止新分配的条目被错误淘汰
- **几何历史长度**：4, 7, 12, 20, 34, 58, 99, 168 — 每个约 ×1.7，覆盖从短程到长程的相关性
- **Useful 半衰**：周期性右移，让长时间不用的条目逐渐变"可替换"

### 参数配置

| 参数 | 值 | 说明 |
|------|-----|------|
| 表数量 | 8 | tagged 表 + 1 base 表 |
| Base 表大小 | 2^13 = 8192 | bimodal 预测 |
| 每张 Tagged 表大小 | 2^12 = 4096 | 共 8 × 4096 = 32768 项 |
| Tag 宽度 | 12 位 | 减少假命中 |
| 历史长度 | 4, 7, 12, 20, 34, 58, 99, 168 | 几何递增 |
| Useful 衰减周期 | 256K | 防止有用条目永久占用 |

### 运行方式

TAGE 使用独立的 `tage.c` 和 `run_tage.sh`。脚本用 `tage.c` 替代 `predictor.c` 编译，生成独立二进制 `predictor_tage`。

## 六、TAGE 的最优性分析

### 为什么 TAGE 比其他方法都好？

**1. 多尺度历史匹配 — 解决了"固定历史长度"的根本缺陷**

之前所有方法都用固定的历史长度。但程序中不同分支的相关性跨度差异巨大：
- 简单的 if-else 可能只需 4 条历史就能预测
- 虚函数调用、多态循环可能需要 100+ 条历史才能捕获跨函数的相关性

TAGE 的 8 张表用几何递增的历史长度（4 到 168），**自动为每个分支选择最佳历史长度**。长历史的表捕获远距离相关，短历史的表避免噪声。

**2. Tag 机制 — 精准匹配，拒绝"假命中"**

gshare/Perceptron 的 index 查找是无条件的——查到什么就用什么。TAGE 加了 tag 校验：即使 index 碰撞，tag 不匹配就不算命中，强制退回到更短但更可靠的表。这大幅减少了 aliasing 导致的误预测。

**3. Useful 计数器 + 半衰 — 自适应资源管理**

Useful 计数器解决了一个核心矛盾：何时淘汰旧条目为新分支腾空间。直接替换可能丢失有价值的信息，永不替换则新分支无法获得表项。TAGE 的方案：
- 预测正确时 useful++，错误时 useful--
- 新条目只替换 useful=0 的旧条目
- 周期性半衰（所有 useful >>= 1）让长期不用的条目自然老化

**4. Provider-Alternate 置信度判断**

当 provider（最长匹配表）的 useful=0 时，TAGE 不盲目信任它，而是退回到 alternate（次长匹配或 base）。这避免了新分配但尚未充分训练的条目引入误预测。

**5. 相比 Perceptron 的结构性优势**

| 维度 | Perceptron | TAGE |
|------|-----------|------|
| 历史长度 | 固定 20 位 | 8 个尺度自动选择 |
| 特征 | 仅全局历史 | 全局历史 + tag 精准匹配 |
| 表大小 | 1024 项 | 32768 项 + 8192 base |
| 非线性能力 | 无（线性模型） | 有（分段线性，多表组合） |
| 别名处理 | 无 | tag + useful 双重保护 |

TAGE 的存储开销约为 Perceptron 的 30 倍，但换来的准确率提升是显著的——这符合分支预测领域"用存储换准确率"的基本 tradeoff。
